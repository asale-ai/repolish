# 01 · Architecture

[English](01-architecture.md) · [中文](01-architecture.zh-CN.md)

## Why Rust

- **One static binary.** Download and run inside a GitHub Action, cold start under a
  second, no runtime to install. This is the single reason a tool like scorecard can be
  adopted widely.
- **Fast.** Walking a large repository and reading its git history finishes in
  milliseconds, so it can run as a pre-commit hook.
- **WASM later, if wanted.** The same check logic could run in a browser without a second
  implementation.

**The cost, stated plainly:** the LLM ecosystem is thinner than Python's, so anything in
that direction means writing more glue. That is manageable — an LLM call is a POST with
JSON, not a framework. The genuinely hard part was rewriting Markdown without damaging it,
and the answer we arrived at is not the one this document originally assumed. See
[Design three](#design-three-markdown-editing-happens-at-the-text-layer).

## Workspace layout

```
repolish/
├── crates/
│   ├── repolish-core/      # Check trait, Evidence, score aggregation, the Report model
│   ├── repolish-ingest/    # Ingestion: file tree, manifests, git history, languages, profile detection
│   ├── repolish-checks/    # The checks themselves
│   ├── repolish-md/        # README parsing, section identification, line-level editing
│   ├── repolish-render/    # Terminal report, REPOLISH.md, badge.json, SVG cards, the recorder
│   └── repolish-cli/       # The only binary
├── action/                 # Composite action definition and usage examples
├── assets/                 # Brand files, generated by repolish-render's logo example
├── skills/                 # The agent skill, from the `skill` stage
├── demo/                   # The sample repository the demo recording is made against
└── docs/
```

**The hard boundary: nothing in the scoring path may depend on a model.** Scoring has to be
purely deterministic. A model may generate suggestion text; it must never influence a
number, because a score that cannot be reproduced makes the badge worthless. There is no
LLM crate today, and adding one must not change that boundary.

## Crate choices

| Concern | Choice | Why |
|---|---|---|
| CLI arguments | `clap` (derive) | Uncontroversial |
| File walking | **`ignore`** | ripgrep's own crate; respects `.gitignore` for free, and `.repolishignore` falls out of it |
| Git history | **`gix`** | Pure Rust, no libgit2 or C dependency, so static linking keeps working. Activity and release cadence come from here |
| GitHub API | ~~`octocrab`~~ → **`ureq`** | The remote need is one `GET /repos/{owner}/{repo}`. octocrab drags in tokio and hyper, turning a fully synchronous CLI asynchronous and slowing the multi-platform static build. Blocking `ureq` (ring backend, no cmake/nasm on Windows) |
| Markdown | **`comrak`** | GFM-compatible, and its `sourcepos` gives the line numbers the editing layer needs |
| Manifests | `toml` + `serde_json` | Cargo.toml / package.json / pyproject.toml / go.mod are parsed directly |
| Errors | `anyhow` + `thiserror` | Nothing more is needed: the CLI's user-facing errors are written by hand, per message |
| Path handling | `dunce` | Windows UNC paths, otherwise printed back to the user as `\\?\C:\…` |

**The dependency list is short on purpose, and shorter than this document once planned.**
Earlier drafts chose `tokei` for language statistics, `minijinja` for SVG templating,
`rayon` for parallel checks, `miette` for diagnostics, and `insta` for snapshots. None of
them are dependencies:

- **Language statistics** are a file-extension tally (`repolish-ingest/lang.rs`). The card
  says "by file", and counting files needs no library.
- **SVG** is written by string concatenation in `repolish-render/draw.rs`. A template
  engine would put the layout in one language and the geometry in another; the drawings
  are generated, never authored by hand.
- **Parallelism** was never needed — the whole run is already in the millisecond range.
- **Diagnostics** are printed by our own renderer, because the terminal report has a
  specific shape (score, bands, dot grid, findings) that a generic diagnostic crate does
  not produce.
- **Snapshot tests** would have frozen output that changes for good reasons; the tests
  assert invariants instead (self-containment, determinism, nothing drawn outside the
  card).

Every one of those is a dependency **not** taken. That is the point of listing them.

Deliberately excluded: `axum`, `sqlx`, `moka` — there is no server.

## Design one: the Check trait

The foundation of the engine.

```rust
pub trait Check: Send + Sync {
    fn id(&self) -> &'static str;              // "readme-quickstart"
    fn risk(&self) -> Risk;                    // Critical/High/Medium/Low → weight 10/7.5/5/2.5
    fn requires_remote(&self) -> bool;         // needs the GitHub API
    fn applies_to(&self, p: Profile) -> bool;  // applicability by project type
    fn run(&self, ctx: &RepoContext) -> Outcome;
}

pub enum Outcome {
    /// Decided
    Scored { score: u8, evidence: Vec<Evidence>, fixes: Vec<Fix> },
    /// This project type does not need it, decided by Profile
    NotApplicable { profile: Profile },
    /// We wanted to check and objectively could not
    Inconclusive { reason: String },
    /// Not run because of configuration or mode (no --remote, --skip)
    Skipped { reason: String },
}
```

The four terminal states differ in **reporting and badge behaviour**, not just meaning:

| State | Counts in the denominator | Listed under "not verified" | Affects the badge |
|---|---|---|---|
| `Scored` | ✅ | | |
| `NotApplicable` | ❌ | ❌ | ❌ |
| `Inconclusive` | ❌ | ✅ | ❌ |
| `Skipped` | ❌ | ✅ | ✅ labelled |

Separating "I did not check", "this project does not need it" and "I checked and it
failed" **in the data model** is what lets the report be honest.

### Aggregation

Risk-weighted, following scorecard, with only `Scored` checks in the denominator:

```
total = Σ(score_i × weight_i) / Σ(weight_i) × 10
```

**No category-level weights.** Two layers of weighting make the effect of any change
impossible to reason about. Category scores are display only.

**Denominator protection:** if the weight of `Scored` checks is under 50% of the weight
registered for this run, no total is reported — only the per-check breakdown and the
reason. Otherwise "we checked three things and they passed" reads as 100/100.

Full detail in [03-scoring](03-scoring.md).

## Design two: offline first

```
repolish --stages check           → local only, no network, no key, instant
repolish --stages check --remote  → adds GitHub API metadata
```

**The default path runs with zero configuration.** For a CLI, that is the difference
between being adopted and not.

**Local and remote scores use different denominators** — three remote checks become
`Skipped` and drop out — so the two numbers are not comparable. `badge.json` therefore
carries a `mode` field, and the badge label says `(local)` when it is one.

## Design three: Markdown editing happens at the text layer

This was the hardest part, and the plan changed once it met reality.

The original design was: parse with `comrak`, edit the AST, serialise back with
`format_commonmark`. **That approach was measured and abandoned.** The round trip is lossy
— reference-style links get flattened, setext headings become ATX, `*` list markers become
`-`, tabs become spaces. On 12 real-world READMEs it was lossless on **zero** of them. The
experiment is still in the repository as `repolish-md/examples/roundtrip.rs`, because the
result is the reason for the current design.

So `polish` works at the text layer instead:

1. `comrak` parses the README and the AST answers one question only: **which line**
   (`sourcepos`).
2. The original text is split at those lines and spliced back together.
3. Every other byte is untouched — tabs, CRLF, list markers, reference-style link
   definitions all survive exactly.

`repolish-md` is therefore a **read-only** crate: it never produces text. Editing lives in
`edit.rs` as line insertion.

**The consequence is a hard invariant: `polish` only inserts.** It cannot reformat, cannot
reorder, and cannot delete. That is not caution for its own sake — a tool that teaches
people to tidy their repository has no business reflowing their prose.

## Profile detection

`repolish-ingest` decides the project type during ingestion (`library` / `app` / `cli` /
`docs` / `collection` / `meta`), which drives each check's `applies_to`. The criteria and
the non-applicability rules are in [03-scoring](03-scoring.md).

Detection can be overridden by `profile` in `.repolish.toml` or by `--profile`, and the
result **must appear in the report** — otherwise an author is left wondering why some
checks vanished.
