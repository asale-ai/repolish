# 01 · 技术架构

## 为什么 Rust

- **单静态二进制**：GitHub Action 里下载即用，冷启动 <1s，无运行时依赖。scorecard 能铺开的核心原因就是这个。
- **快**：大仓库的文件遍历 + git 历史分析在毫秒级完成，可以当 pre-commit 钩子用。
- **将来可编 WASM**：同一套检查逻辑能跑在浏览器里，不必写两份。

**代价（需承认）：** LLM 生态比 Python 薄，`repolish-llm` 要多写胶水代码；Markdown 的 AST 往返改写工作量不小。前者可控（LLM 调用本质是 HTTP + JSON，不需要框架），后者是真正的技术难点，见下文。

## Workspace 结构

```
repolish/
├── crates/
│   ├── repolish-core/      # Check trait、Evidence、评分聚合、Report 模型
│   ├── repolish-ingest/    # 仓库摄取：文件树、依赖清单、git 历史、LOC、Profile 探测
│   ├── repolish-checks/    # 各检查项的具体实现
│   ├── repolish-md/        # README 解析 / 区块识别 / 增量改写（AST 往返）
│   ├── repolish-llm/       # 多 provider 抽象，optional feature
│   ├── repolish-render/    # 终端报告 / REPOLISH.md / badge.json / SVG 卡片与 logo
│   └── repolish-cli/       # 唯一二进制
├── action/                 # composite action 定义与用法示例
├── assets/                 # 品牌文件，由 repolish-render 的 logo example 生成
├── fixtures/               # 测试用真实仓库快照
└── docs/
```

**硬性边界：`repolish-core` 不依赖 `repolish-llm`。** 评分必须是纯确定性的，LLM 只参与生成建议文本。否则分数不可复现，徽章就没有公信力。

## crate 选型

| 模块 | 选型 | 理由 |
|---|---|---|
| CLI 参数 | `clap`（derive） | 无争议 |
| 文件遍历 | **`ignore`** | ripgrep 同款，自动尊重 `.gitignore`，天然支持 `.repolishignore` |
| Git 历史 | **`gix`** | 纯 Rust，无 libgit2 / C 依赖，静态编译不破功。活跃度、贡献者、release 节奏由此取得 |
| GitHub API | ~~`octocrab`~~ → **`ureq`** | 远程需求只有一个 `GET /repos/{owner}/{repo}`。octocrab 会带进 tokio + hyper，把这个全同步的 CLI 拖成异步，也拖慢 M3 的多平台静态二进制。改用阻塞式 `ureq`（ring 后端，Windows 上无需 cmake/nasm） |
| 代码统计 | **`tokei`**（作为库） | 直接给出语言分布 + LOC，同时用于 Profile 探测 |
| Markdown | **`comrak`** | GFM 兼容，且 `format_commonmark` 能把 AST **序列化回 Markdown**。`pulldown-cmark` 只解析不往返，做不了增量改写 |
| 依赖清单 | `toml` + `serde_json` + `cargo_metadata` | package.json / pyproject.toml / go.mod / Cargo.toml |
| 模板 | **`minijinja`** | 运行时模板，用户可自定义区块与 SVG 风格，无需重编译 |
| 并行 | `rayon`（检查项）+ `tokio`（网络） | 检查项之间天然并行 |
| 错误 / 诊断 | `thiserror` + **`miette`** | miette 输出带源码片段和高亮 span 的诊断，正好是 repo-audit 那种「文件 + 行号 + 证据」的形态，免费获得 |
| LLM | `reqwest` 自封一层薄客户端 | 不引重框架。Messages API 就是一个 POST |
| 测试 | **`insta`** 快照测试 | 生成类输出（README、报告、SVG）用快照测最省力 |
| 发布 | ~~`cargo-dist`~~ → **手写 release workflow** | 归档命名是 action 下载 URL 的契约，手写让两边在同一个仓库里可以对照检查；也少一个无法在本地验证的构建期依赖。代价是没有 `curl | sh` 安装脚本，待有需要再补 |

> 版本号在初始化 workspace 时再确认，本文档只锁定选型。

已明确**不引入**：`axum`、`sqlx`、`moka`（无服务端）；`plotters`（SVG 用 minijinja 手写模板，可精确控制 dark/light 双主题）。

## 核心设计一：Check trait

整个引擎的地基。

```rust
pub trait Check: Send + Sync {
    fn id(&self) -> &'static str;           // "readme-quickstart"
    fn risk(&self) -> Risk;                 // Critical/High/Medium/Low → 权重 10/7.5/5/2.5
    fn requires_remote(&self) -> bool;      // 是否需要 GitHub API
    fn applies_to(&self, p: Profile) -> bool;  // 项目类型适用性
    fn run(&self, ctx: &RepoContext) -> Outcome;
}

pub enum Outcome {
    /// 已判定
    Scored {
        score: u8,                 // 0-10
        evidence: Vec<Evidence>,
        fixes: Vec<Fix>,
    },
    /// 该项目类型不需要此项（由 Profile 决定）
    NotApplicable { profile: Profile },
    /// 想查但客观查不了——抄 repo-audit 的覆盖限制声明
    Inconclusive { reason: String },
    /// 用户配置或运行模式导致未执行（如缺 --remote、被 --skip）
    Skipped { reason: String },
}

pub struct Evidence {
    pub file: PathBuf,
    pub span: Option<Range<usize>>,   // miette 直接渲染成带高亮的源码片段
    pub note: String,
}

pub struct Fix {
    pub severity: Severity,           // P1 / P2 / P3
    pub message: String,
    pub patch: Option<Patch>,         // 可自动应用的变更
}
```

四种终态的差别在于**报告与徽章行为**，不只是语义：

| 状态 | 计入分母 | 进「覆盖限制」 | 影响徽章 |
|---|---|---|---|
| `Scored` | ✅ | | |
| `NotApplicable` | ❌ | ❌ | ❌ |
| `Inconclusive` | ❌ | ✅ | ❌ |
| `Skipped` | ❌ | ✅ | ✅ 标注 |

把「我没检查」「这个项目不需要」「我检查了不合格」在数据层分开，报告才能诚实。

### 聚合算法

沿用 scorecard 的风险加权，分母只含 `Scored` 项：

```
总分 = Σ(score_i × weight_i) / Σ(weight_i) × 10
```

**不设类级权重**——双层权重会让调参影响无法推理。类别得分仅作展示。

**分母保护：** 若 `Scored` 项权重和不足本次运行注册的检查项权重和的 50%，不输出总分，只输出分项报告并说明原因。防止「大部分没查 → 剩下几项满分 → 100/100」的虚高。

详见 [03-评分维度.md](03-评分维度.md)。

## 核心设计二：离线优先

```
repolish check .           → 纯本地，无网络无 key，秒出分数
repolish check . --remote  → 补 GitHub API 元数据
repolish polish . --llm    → 生成改写文本
```

`repolish-llm` 放在 optional feature 后面。**默认路径零配置能跑**，这是 CLI 采用率的生死线。

**注意：本地分与远程分基准不同**（三个远程检查项会变成 `Skipped`，被剔出分母），二者数值不可横向比较。因此 `badge.json` 必须带 `mode` 字段，local 模式的徽章 label 要标注出来。

## 核心设计三：Markdown 增量改写

最难的一块，需尽早动手。

**流程：**

1. `comrak` 解析 README 得到 AST
2. 按 heading 切分区块
3. 区块分类器：正则 + 别名表，把 `Getting Started` / `Quick Start` / `快速开始` 归一到 `quickstart`
4. 只对缺失或薄弱的区块做 AST 级插入 / 替换，**保留作者原有文风与其余内容**
5. `format_commonmark` 输出

**这是与 readme-ai 的核心差异**：不重写，只补缺。

**风险控制：** 先用 `fixtures/` 中 30 个真实 README 建立「改一个字符也不能动别的地方」的往返测试（`insta` 快照），再往上加功能。这块不稳，后面所有「自动改写」的信任都建立不起来。

## Profile 探测

`repolish-ingest` 在摄取阶段判定项目类型（`library` / `app` / `cli` / `docs` / `collection`），驱动检查项的 `applies_to`。判据与不适用规则见 [03-评分维度.md](03-评分维度.md)。

探测可被 `.repolish.toml` 的 `profile` 或 `--profile` 覆盖，且**必须在报告中显示探测结果**——否则作者会困惑于「为什么少了几项」。
