# 06 · 路线图

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| **M1** | `ingest` + `core` + 8 个纯本地检查 + 终端报告 | 同一 commit 重复运行分数完全一致；在 10 个真实仓库上人工复核分数合理 |
| **M2** | 补齐全部检查项 + `--remote` + JSON schema 冻结 + `--min-score` | 能作为 CI 门禁使用；JSON 输出结构定稿 |
| **M3** | `badge` + `report` + `init` + composite action + cargo-dist 首个 release | **GitHub 代码搜索能搜到外部仓库挂了 badge** |
| **M4** | `repolish-md` 增量改写 + `polish --apply` | 30 个 fixture README 的往返测试全绿；改写不破坏原文 |
| **M5** | `repolish-llm` + LLM 增强建议 | — |

## 关键判断

**M3 是生死线。** 在此之前不要碰 LLM——分数本身立不住的话，AI 生成的内容也没人信。

M1 的 8 个检查项全部选择**无需网络**的（见 [05-评分维度.md](05-评分维度.md)），确保默认路径零配置可跑。

M4 之前先建 `fixtures/`：收集 30 个真实 README（覆盖不同语言、长度、风格），作为增量改写的回归基线。

## 明确的非目标

- 托管服务、排行榜、Web 站点
- 代码质量 / 安全扫描（scorecard 已做好，必要时在报告里链接过去而非重复实现）
- 从零生成 README（readme-ai 的领域）

## M1 完成情况（2026-08-19）

已交付：workspace 六个 crate、`Check`/`Outcome` 四态模型、风险加权聚合与分母保护、Profile 探测、8 个本地检查项、终端与 JSON 输出、5 个退出码。`cargo test` 6/6 通过；同一 commit 重复运行输出逐字节一致。

**与设计文档的偏差（有意为之，非遗漏）：**

| 项 | 实际做法 | 原因 |
|---|---|---|
| 语言统计未用 `tokei` | 按扩展名自行计数 | M1 只需粗粒度信号；`tokei` 编译成本高，M2 接入时一并做语言分布 |
| `gix` 只取 HEAD 提交时间 | 未做贡献者 / release 节奏 | `activity` 检查项够用；M2 补 |
| 分母保护的分母 | 本次运行**注册**的检查项，而非 v1 全部 22 项 | 否则 M1 只注册 8 项（占 v1 总权重 49%）会永远触发保护、永不出分 |
| 内容统计排除点目录 | `.trae/`、`.vscode/` 等不计入语言统计 | 实测中 `.trae/skills/` 里的 6 个 md 把一个空仓库误判成文档站 |

**新增的工程约束：**

- `tests-present` 必须识别内联测试（Rust `#[cfg(test)]`、Go `func Test`），且标记须在行首——否则会命中源码里的字符串字面量（本检查项一度扫中了自己的 `INLINE_MARKERS` 定义）
- Windows 上路径统一走 `dunce::canonicalize`，避免 `\?\` 前缀泄漏到用户可见输出
