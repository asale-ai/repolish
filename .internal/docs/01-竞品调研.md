# 01 · 竞品调研

调研对象见 [参考.txt](参考.txt)。结论：7 个项目各自覆盖了目标产品的一块能力，**没有一个把「诊断 → 生成 → 可视化 → 回链传播」打通**。

---

## 1. ossf/scorecard

> https://github.com/ossf/scorecard — OpenSSF（Linux 基金会）出品，仓库安全评分的事实标准。

对仓库执行 23 项自动化检查：

| 类别 | 检查项 |
|---|---|
| 文档 / 合规 | License、Security-Policy、CII-Best-Practices |
| 流程 | Code-Review、Branch-Protection、CI-Tests、Contributors、Maintained |
| 供应链 | Pinned-Dependencies、Dependency-Update-Tool、Signed-Releases、Packaging |
| 代码安全 | SAST、Fuzzing、Vulnerabilities、Binary-Artifacts、Dangerous-Workflow、Token-Permissions、Webhooks |

**可借鉴：**

- **风险加权聚合**：每项 0–10 分，按风险等级加权求平均（Critical 10 / High 7.5 / Medium 5 / Low 2.5），而非简单平均。
- **三种交付形态**：CLI 二进制 + GitHub Action + REST API。
- **徽章闭环**：跑过 Action 即可在 README 挂自动更新的分数 badge，点击进入 `scorecard.dev/viewer` 详情页。**这是「让作者主动挂链接」的成熟范式**。

**局限（= 我们的空档）：** 只管安全，完全不涉及 README 质量、description、topics、可读性。

## 2. eli64s / readme-ai

> https://github.com/eli64s — Eli Salamie，InnerAura 创始人。
> 核心项目 https://github.com/eli64s/readme-ai （3k★，Python）

- **仓库分析引擎**：解析 `pyproject.toml` / `package.json` 提取依赖，`.readmeaiignore` 过滤文件，生成目录树 + 关键模块摘要作为 prompt 上下文。
- **生成区块**：简介 → 功能表 → 项目结构树 → 项目索引 → 快速开始 → 安装/使用/测试 → 路线图/贡献/许可。
- **多 LLM**：OpenAI / Anthropic / Gemini / Ollama / **离线模式**（无 key 也能出模板）。
- **视觉参数化**：`--badge-style`（flat / flat-square / plastic / for-the-badge / social）、`--header-style`（classic / modern / compact / console / banner）、`--logo`、`--emojis`、`--navigation-style`。

**可借鉴：** 仓库分析管线的整体思路；区块体系；视觉风格参数化。

**局限：** 一次性**从零生成**，对已有 README 的成熟项目不友好，不做增量优化。

## 3. InnerAura/hyperweave

> https://github.com/InnerAura/hyperweave — 同一作者，给 Agent 用的 SVG 输出层。

"One API call, one SVG"：把结构化 spec 渲染成自包含 SVG，零依赖，任何 markdown 都能渲染。

- 13+ 种图：pipeline、DAG、状态机、时序图、对比矩阵、benchmark 表、badge、profile card、dashboard。
- **双层设计**：SVG 内嵌 `hw:payload`（完整 JSON spec）+ `hwz/1`（~200 token 带哈希摘要）——人看图，Agent 读数据、可校验可改。
- 4 套视觉基因组（brutalist / automata / chrome / primer），提供 CLI + HTTP API + MCP。

**可借鉴：** 自包含 SVG 的形态；「图里嵌数据」使产物可被机器复读。

## 4. conorbronsdon/repo-audit

> https://github.com/conorbronsdon/repo-audit — Claude Code / Codex 的 skill，开源发布前的可信度审计。

核心问题：**README 说的和代码干的一致吗**。

- 凡是 README 宣称「防止 / 阻止 / 保证」某事的，就去代码里找强制机制。
- 三级判定：**真强制**（hook / CI job / 测试） vs **仅告警**（advisory） vs **只是文字建议**（零约束）。
- 输出：P1/P2/P3 分级发现 + 已验证清单 + **证据链接（文件 + 行号）** + **显式声明「覆盖限制：哪些验证不了、为什么」**。

**可借鉴（优先级最高）：** 这套「证据 + 承认盲区」的报告格式是可信度最高的一种，直接采用。开源作者最反感瞎打分的 linter。

**局限：** 只是 prompt skill，无工程化、无持续监测。

## 5. readme.so

> https://readme.so/ — 拖拽式 README 编辑器。

左侧选区块（Title / Installation / Usage / API / Contributing / License / Badges / FAQ…），中间排序，右侧实时预览，导出 Markdown。纯手工，无 AI，无仓库分析。

**可借鉴：** 验证了「**区块化 = 用户心智模型**」；低门槛 Web 入口带来巨大流量。

---

## 6. Gitee README 生成

> https://help.gitee.com/ai-productivity/readme-generation — 平台内建能力。

Gitee Agent 分析依赖、配置文件、代码结构 → 一键「生成 README」或「README 优化」。内置项目简介、快速开始、使用指南等模块。

**可借鉴（关键）：交付方式**。结果不是丢一段文本给你，而是**自动开一个轻量级 PR**，用户在 PR 页面 review + 预览 + 合并。

推论：优化建议应以**可合并的变更**形式落地，而非「你自己去改吧」的报告。合并率即北极星指标。

## 7. pingcap/ossinsight

> https://github.com/pingcap/ossinsight — 分析 10 亿+ 行 GitHub Event 数据（底层 TiDB）。

- 仓库分析（star/fork/贡献者增长、地理分布）、开发者分析、项目对比、趋势排行。
- 自然语言提问 → 自动生成 SQL + 可视化。
- **Widget 体系**：`https://next.ossinsight.io/widgets/official/analyze-repo-stars-history?repo_id=xxx` 直接返回 SVG，官网提供可复制的 `<picture>` 代码（dark/light 双主题 + `image_size` 参数），贴进 README 即为实时更新的图 + 回链。
- 公共 REST API `api.ossinsight.io/v1`，以及 `/llms.txt`。

**可借鉴：** widget URL 参数化 + dark/light 双主题的 `<picture>` 写法。这与 [star-history](https://github.com/star-history/star-history) 是同一套增长套路。

## 汇总：谁补哪一块

| 能力模块 | 可借鉴来源 | 空档（机会） |
|---|---|---|
| 诊断评分引擎 | scorecard：检查项定义、风险加权、JSON schema | scorecard 只测安全；**文档质量、description、topics、可发现性无人评分** |
| 一致性审计 | repo-audit：证据链、P1/P2/P3、覆盖限制声明 | 仅是 prompt skill，无工程化 |
| README 生成 | readme-ai：分析管线、区块体系、视觉参数化；readme.so：区块心智 | 两者都是一次性生成，不做「诊断 → 定位 → 只改该改的」增量优化 |
| 可视化 | hyperweave：自包含 SVG；ossinsight：widget 参数化 | 无人做**「仓库健康度」本身的可视化** |
| 数据统计 | ossinsight：分析维度、对比视图、公共 API | 重基础设施，可做轻量版或直接调其 API |
| 交付 / 传播 | Gitee：自动 PR；scorecard：badge；ossinsight/star-history：SVG 回链 | **没有产品把这四步串起来** |

## 差异化结论

> scorecard 管**安全**，readme-ai 管**从零写**，OSSInsight 管**看数据**，repo-audit 管**发布前体检**——
> **没人管「一个已经存在的开源项目，怎么让它被更多人看懂和发现」。**
